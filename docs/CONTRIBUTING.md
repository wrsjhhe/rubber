# 开发交接与审核

## 开发者

1. 阅读功能、技术、架构和进度；选择依赖已满足的 M 任务，填写负责人和范围。下一项默认 M2。
2. 按验收实现，保留既有接口和回归；规格不足先补设计并记录待决事项，不静默修改数据和所有权契约。
3. 新增契约和失败路径测试。C++ 每语句独立行、运算符留空格、逻辑块分段、中文注释、UTF-8 无 BOM，遵循 .clang-format。
4. 执行适用验证并保存命令和输出；未运行注明原因，不把计划写成已通过。
5. 更新 PROGRESS 对应任务和交接记录，标为待审核，提交确切版本、变更清单、缺项与证据。

## 验证基线

在仓库根目录使用 x64 Developer PowerShell，选择独立测试预设：

```powershell
cmake --preset tests
cmake --build --preset tests
ctest --preset tests
..\rubber-build\tests\sensor_check.exe --validation
..\rubber-build\tests\gallery.exe --smoke --validation
..\rubber-build\tests\shadow_demo.exe --smoke --validation
..\rubber-build\tests\sensor_demo.exe --smoke --validation
```

验证层需安装；运行前检查测试支持的参数。新增测试加入 CTest。安装验收必须真正使用安装前缀。只改文档不用重跑 GPU 测试，但须检查链接、状态和代码事实。

## 审核者

收到代码后针对确切版本独立审核，不能把开发者进度描述或自测当作审核通过。后续可由 Codex 按此清单审核：

- 逐条映射功能编号与验收，指出漏项和范围变化。
- 检查依赖、接口、所有权是否真正分离，避免只移动目录就宣称完成框架。
- 检查布局/屏障、资源依赖、GPU 未完成时释放、缓存代际、结果保活、异常路径、Busy 回收和外部消费者寿命。
- 检查深度/颜色/速度语义、历史失效、相机隔离、调试与真值隔离。
- 检查模块能否通过协议扩展，核心是否引入窗口依赖。
- 独立运行适用测试，查看 validation、图像和性能证据；无法运行则明确验证缺口。

问题编号如 R-M2-001，记录严重性、文件/行、触发条件、影响、修复要求和复测方法。资源寿命错误、结果污染、崩溃、主要验收漏项属于阻塞问题；风格建议单列。

结论为通过、需修改或无法完整验证。开发者修复后更新同一问题记录，审核者复查；必需验收和阻塞问题关闭后才标记已验收。本文不授权自动发送消息或代码给其他人。

## 文档归属

FEATURES 维护功能范围；TECHNICAL_DESIGN 维护数据/算法/同步约束；ARCHITECTURE 维护组件/依赖/所有权；PROGRESS 是唯一进度来源；README 保留运行说明，FRAMEWORK 是入口。修改公开接口同时更新使用示例，避免目标能力被写成已实现。
